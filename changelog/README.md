## 增量记录口径

更新交接文档或更新日志时，先确认这份文档上一次更新对应的日期和 Git 提交，再核对从该时间点到当前的完整 `git log`、`git diff` 与验收记录。记录范围覆盖这段期间内完成的全部功能、交互、视觉、数据逻辑、回退结论和验证结果，不能只根据最近一两轮对话整理。

- 已经写入该文档的事项不重复抄写。
- 同一天或同一批未发版改动优先补进现有「未发版」章节。
- 中途探索过、最终已回退的方案，要同时写清探索结果与当前生效状态，避免接手人把实验代码当成正式效果。
- 更新完成后再对照源码差异检查一遍，确认每个用户可感知变化都有归属。
- 没有明确发版要求时保持现有版本号，只更新「未发版」内容和当前交接状态。

## 什么时候写

只要用户说「升级版本号」「对齐版本号」「发一版」，就必须同时：

1. 改对应端的版本号（Android：`app/build.gradle.kts` 的 `versionName` / `versionCode`；iOS：`iOS/Punctum/project.yml` 的 `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`，改完后在 `iOS/Punctum` 执行 `xcodegen generate`）。
2. 在对应端的 changelog **最上面**加一节，日期用当天。
3. 更新根目录 `CHANGELOG.md` 里的「当前版本」一行。

没有升版本号的日常改动，不必另开一节；等下次升版本时并进那一节。

例外：用户明确说「更新交接日志 / 给同事接手」时，即使不升号，也要在对应端日志 **最上面** 加一节 `## 未发版 · YYYY-MM-DD`，并更新根目录「当前交接状态」。下次升版本时把「未发版」改成正式版本号，不要另起一节重复抄。

## 每一节怎么写

标题格式：

```
## 0.x.y · YYYY-MM-DD
```

正文先用两三句说这一版对用户意味着什么，再按主题列条目。条目写「为什么 / 用起来怎样」，不要只罗列文件名。

历史版本的构建号曾与展示版本对应，例如 `0.5.1` → `51`。从 iOS `0.5.10` 起，build 按上一构建号递增（`59` → `60`），避免多位补丁号产生歧义；展示版本按正常小版本递增。Android 本轮构建号保持 `59`。

两端版本号默认对齐。若某一端单独发版，只改那一端的文件，并在该节开头标明「仅 Android」或「仅 iOS」。


## 定稿与 GitHub 同步

- 用户在同一版本内确认最终参数时，更新该版本当前说明，明确已确认的具体范围；旧实验保留在历史章节或 design-qa.md，不能继续标成当前默认方案。
- README、iOS/Punctum/README.md、CHANGELOG.md 和 PUNCTUM_HANDOFF.md 使用一致版本、默认参数与最新安装包路径。
- 用户明确要求上传时，同步本次源码、项目配置、测试、文档和构建脚本，上传后独立核对远端分支及文件树。本地提交不等于远端上传成功。
- APK/IPA、签名文件、证书、profile、密码和本地机器配置不纳入 Git。交接以仓库内相对路径为主，本机日志路径只作为历史证据。
